# 工单写作规范（题面叙事优先）

> 这份文档管**内容怎么写**，不管**契约怎么填**。
> 契约（字段、准入门、分支结构）在 [`docs/paper-platform-design.md`](paper-platform-design.md) §4
> 与 [`content/schema/`](../content/schema) 的两个 schema 里；每个 Track 仓自己的约定（阶段分支怎么切、
> `TASKS/*.md` 与 `ticket.yaml` 的关系）写在各仓的 `stages/README.md`。
> 这里只回答一个问题：**同一张工单，为什么有的读起来像一篇工程记录，有的读起来像一叠便签。**
>
> 本文与平台的关系是**平台定规范、内容仓遵守**：规范正文只在本仓存一份，内容仓（例如
> [`seckill-lab`](https://github.com/OnlyblackTea/seckill-lab)）只放指针，不复制一遍——
> 复制出来的第二份迟早和这里漂移。

---

## 0. 一句话规范

> **自然段承载叙事，标题承载语义层级，列表承载真正的并列关系，组件承载交互状态。**

写题面时，脑子里想的是「我要把一个线上问题讲清楚」，不是「我要把信息点列全」。
信息点列全了但读不成句子，学员的阅读路径就会变成：读一句 → 停下来重新建立上下文 → 再读一句。
每停一次，他离「我知道该改什么」就远一步。

---

## 1. 先看页面怎么消费这些字段

题面不是纯文本，它会被渲染成一个有层级的页面。动笔前先知道**每一块会落在哪里**：

| 你写的东西 | 页面上出现在哪 | 谁在读 |
|---|---|---|
| `brief.problem` | 中栏「任务说明」正文，按 Markdown 渲染（`##` → 二级语义区块） | 学员，第一遍就逐字读 |
| `scope.files_to_change` | 「改动面」文件清单（列表） | 学员，动手前对照 |
| `grader.correctness.expect` | 「验收标准」，同样按 Markdown 渲染 | 学员，判断"什么算做完" |
| `hints[].title` + `hints[].text` | 「提示」，**默认全部折叠**，标题是「提示 N：标题」 | 学员，卡住时才展开 |
| `submission.template.require` | 「提交」答辩要求 | 学员，交卷前 |
| `grader.*` 的机器字段 | 「验收标准」上方的测试组 / canonical 测试路径 | 平台与学员 |

三条推论：

1. **折叠区不该抢注意力。** 提示默认是收起来的，所以正文里**不要**把 hints 的内容再复述一遍——
   学员会同时看到「正文里的半截答案」和「提示」。
2. **正文里的 `##` 就是页面上的区块标题。** 用几个、用哪几个，直接决定页面长什么样。
3. **`expect` 是给人读的**。它是学员判断"我做完没有"的唯一依据，所以它和题面一样要能顺读。

## 2. 四条写作规则

### 2.1 一个自然段 = 一个完整语义

**不要「一句话一行」，也不要把一个完整因果拆成多个视觉块。**

不推荐（碎片化）：

```text
库存为 1。

第一次下单。

成功。

库存变成 0。

订单增加 1。

第二次下单。

发生异常。

回滚。
```

也不推荐（超级长段）：

```text
库存为1时第一次下单成功库存变成0订单增加1随后第二次下单发生异常需要回滚……
```

推荐（一个自然段讲完一个场景）：

```text
当商品库存为 1 时，第一次下单应该能够正常完成：系统生成对应订单，商品库存减少 1，
通过 `countByProduct(productId)` 查询订单数量也能观察到对应的变化。

随后用相同的 user 和 product 再次下单，使第二次操作进入异常场景。此时要验证的是事务能否
正确回滚——第一次操作产生的数据不能停在半路，最终数据库必须回到事务一致的状态。
```

### 2.2 只有语义层级变化时才换段 / 加标题

换段的门槛是「话题变了」，不是「这句话有点长」。
加 `##` 标题的门槛更高：它会在页面上生成一个区块，一个工单**两到四个**就够了。

### 2.3 列表只表达真正的并列关系

- ✅ 改动面（两个文件，真并列）
- ✅ 提交时要交的三件东西（真并列）
- ❌ 把一个流程的步骤拆成一串列表项（那是叙事，用自然段）
- ❌ 把一句话的条件拆成 ①②③（那是句子，不是列表）

### 2.4 事实只存一份

题面里**不要**复述判据、hints、提交要求。写「验收标准见 `grader.correctness.expect`」这种指针也不行——
页面上那三块就在正文下面，读者会自己往下走。复述的代价是两份清单迟早悄悄漂移。

## 3. `brief.problem` 的推荐结构

按「发生了什么 → 为什么是问题 → 你要改什么」组织。**平台会自动补上「验收标准 / 提示 / 开始开发 / 结果」四块**
（分别来自 `grader.correctness.expect`、`hints`、界面本身），所以题面里不要再写它们。

````markdown
## 问题背景

用一到两个自然段说明线下/线上发生了什么、谁发现的、为什么值得现在修。
给出可验证的细节（少了什么数据、差了多少单、谁在对账），但不要编造没有的监控数字。

## 问题表现

说明当前实现出现了什么现象、正常情况下应该是什么结果、以及**为什么**会这样。
尽量用连续自然段讲清因果，不要把每个事实拆成单独一行。

## 你需要完成的修改

本题需要修改以下文件：

- `路径/一`：现在是什么状态、要补成什么语义。
- `路径/二`：同上。

如果这里有**顺序约束**（比如"必须先扣库存再插订单"）或**边界约束**（"别在 Java 里拼 SQL"），
把它们写成自然段并讲清理由——顺序不是风格偏好，它是让某条用例真的能验到东西的前提。
````

### 3.1 关于技术细节

SQL 形状、方法签名、错误码、异常类型这类**必须逐字对齐**的东西，可以用代码块或行内代码，
但**解释它们的句子仍然用自然段**：

```markdown
扣库存的 SQL 形状是固定的：`UPDATE product SET stock = stock - 1 WHERE id = #{id} AND stock > 0`，
要按**受影响行数**判断是否扣到——大于 0 才算扣到，等于 0 说明已经售罄。
```

不要写成：

```text
扣库存 SQL：
UPDATE product SET stock = stock - 1 WHERE id = #{id} AND stock > 0

判断：
受影响行数
> 0：扣到
= 0：售罄
```

### 3.2 D2：题面里不能有解法

准入门（`platform_service/admission.validate_track`）会扫 `brief.problem` / `brief.concepts` /
`hints[].title` / `hints[].text` 里的解法行。**给出方向可以，给出答案不行**——
「事务边界应该打在 service 层，想想为什么」可以，
「在 `seckill()` 上加 `@Transactional(rollbackFor = Exception.class)`」不行。

## 4. `grader.correctness.expect` 的写法

`expect` 在页面上是「验收标准」，读者拿它判断自己做完没有。所以：

- 先讲**初始状态为什么是红的**（红在哪、为什么这是"红在正确的地方"）；
- 再按**场景**分段讲改对之后应该发生什么，一个场景一个自然段；
- 需要点出关键机制时，用一句话讲清"这条用例到底在验什么"，而不是罗列断言。

推荐：

```yaml
expect: |-
  初始为【红】，且必须红在这两个原因上：……（写清是哪两个，以及为什么这两个才算数）。

  改对后为【绿】。正常下单时，`seckill_order` 里会生成对应订单，订单 id 由 `useGeneratedKeys`
  自动回填（因此不能为空），`quantity`/`status`/`amount` 都取工单约定的值；随后该商品库存减少 1，
  `countByProduct(productId)` 的返回值增加 1。

  第二个场景是先成功下一单，再用**同一 user + 同一 product** 再下一单，让第二次操作撞上唯一键冲突。
  此时第一次下单产生的数据不应该留在最终状态里：商品库存必须与第一次下单后完全相同，
  订单数量也不增加。换句话说，这条用例验的不是"异常能不能抛出来"，而是异常发生之后整个事务
  能不能保持一致——**没有回滚，就会出现"库存扣了但订单没建"的经典丢单**。
```

不推荐：把每个断言拆成一行，读者需要在脑子里重新拼装因果关系。

> 注意：`expect` 是**对红绿形状的描述**，不是判据本身。真正的判据是 canonical 测试。
> 两者不一致时以测试为准，并回来把 `expect` 改成实测到的形状。

## 5. `hints` 的写法

每张工单三到四条，**阶梯式**：H1 给方向，越往后越接近答案，但都不给答案。

### 5.1 结构：`title` + `text`

`hints` 的每一项是 `{id, title, text}`：

- `title`：三到八个字，页面上显示成「提示 N：事务边界」。**必写**——没有标题的折叠项，
  读者不知道要不要展开它，只能一条条点开试。
- `text`：**一个自然段**。优先写成**问句**，逼学员自己想，而不是把结论递过去。

```yaml
hints:
  - id: H1
    title: 事务边界
    text: "`@Transactional` 应该打在哪个方法上？事务边界放在 controller、mapper 和 service 层分别会带来什么后果？"
  - id: H2
    title: 异常回滚
    text: "「异常时回滚」不是自动成立的：Spring 默认只对哪一类异常回滚？把 `rollbackFor` 的默认值查清楚，再想你这张工单的链路上会抛什么。"
  - id: H3
    title: 怎么验证
    text: "改代码前后各跑一次同一条查询（商品的 stock 与订单数），用两次输出的差值证明回滚到底发生没有。"
  - id: H4
    title: 再想一层
    text: "如果两次数据访问的顺序调过来，这条用例还能验到回滚吗？为什么？"
```

### 5.2 几条硬要求

- 一条 hint 只解决一个疑问，不要把三条 hint 的内容塞进一条；
- 不要在 hint 里给出可直接照抄的最终代码；
- id 用 `H1`/`H2`…，页面按顺序显示，所以顺序就是阶梯顺序；
- 展开 hint 会进入学习者画像（设计 §10），所以 hint 只该在"自己想不出来"时才有价值。

## 6. 发布前自检清单

改完 `ticket.yaml`（尤其是改了题面或判据）之后：

- [ ] `brief.problem` 里的每个自然段都能独立读懂，且段与段之间是**话题**在变，不是长度在变；
- [ ] 正文里没有复述判据 / hints / 提交要求；
- [ ] `brief.problem` 里的 `##` 区块不超过四个，且名字能让读者预期下一段讲什么；
- [ ] `grader.correctness.expect` 是按场景分段读得通的，不是断言清单；
- [ ] 每条 hint 都有 `title`，`text` 是一个自然段，且都没给出最终答案；
- [ ] 题面 / concepts / hints 里没有解法行（准入门会扫）；
- [ ] 改了题面或判据 ⇒ **bump `identity.ticket_version`**（旧 TicketInstance 变 stale，设计 §9.2）；
- [ ] 内容仓的 `TASKS/stage-NN.md` 叙述视图同步过了（它是给人读的视图，事实仍只在 ticket.yaml 里存一份）；
- [ ] 如果改到内容仓 `runtime` 指向的文件，重跑那个仓的 `scripts/digest-pin.sh`。

## 7. 迁移状态（以示例 Track `seckill-lab` 为例）

新规范的落地是**逐张迁移**的，不是一次性重写：重写题面要 bump `ticket_version`，
而 bump 会让学员手里那张旧工单变 stale，所以只在真正要改这张工单时顺手迁移。

| Stage | 题面 / 判据 | hints 带 `title` | 说明 |
|---|---|---|---|
| stage-02-order-transaction | ✅ 已按本规范重写 | ✅ | 第一张样板（`ticket_version: 2`），也是"顺手把事实按骨架校正一遍"的例子 |
| stage-01 / 03 / 04 / 05 / 06 | ⬜ 待迁移 | ⬜ | 改到哪张，顺手把哪张迁移掉 |

> 迁移不是必须的紧急事项：没迁移的工单仍然完全合法（`title` 是可选字段）。
> 但**新增**工单一律按本规范写；本仓内置的 demo Track 也已经带上 `title`（`platform_api/demo_repo.py`）。

---

## 8. 一句话总结

> 学员读完题面之后，如果脑子里留下的是一条连续的因果链——「线上出了什么问题 →
> 为什么会有这个问题 → 我要改什么 → 改成什么样才算对」——那这张工单就写对了。
